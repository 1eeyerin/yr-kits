# 의미 단위 커밋

현재 작업 트리의 변경사항을 읽고, 관련 있는 변경끼리 묶어 커밋하세요. 사용자 입력에 커밋 범위나 의도가 있으면 우선 적용하세요.

## 변경사항과 규칙 확인

```bash
git status --short
git diff
git diff --staged
```

- 추적되지 않은 파일도 내용을 확인하세요. 삭제·이름 변경·이미 스테이징된 변경을 빠뜨리지 마세요.
- 프로젝트 지침, `.husky/commit-msg`, commitlint 설정에서 실제 커밋 규칙을 확인하세요. 규칙이 없을 때만 `<type>: <summary>`를 사용하세요.
- 기본 타입은 `feat`, `fix`, `refactor`, `style`, `docs`, `test`, `chore`, `perf`, `ci`, `revert`입니다.
- 기존 staged 변경이 이번 커밋 범위와 다르면 함께 커밋하거나 임의로 해제하지 말고, 처리 범위를 확인하세요.

## 분리와 커밋

1. 같은 기능, 버그 수정, 리팩터링, 문서, 테스트, 설정 변경을 함께 묶으세요. 독립적으로 설명하고 되돌릴 수 있는 변경은 별도 커밋으로 나누세요.
2. 사용자가 지정한 범위에 포함되는 변경만 선택하세요. 파일 안에서 범위가 섞였으면 hunk 단위로 나누고, 판단할 수 없으면 확인하세요.
3. 각 단위에서 필요한 파일만 스테이징하고 최종 diff를 확인한 뒤 커밋하세요.

```bash
git add -- <관련-파일>
git diff --staged
git diff --cached --check
git commit -m "<저장소-규칙에-맞는-메시지>"
```

4. 커밋 후 상태를 확인하고, 남아 있는 승인된 변경이 있으면 반복하세요.

```bash
git log -1 --oneline
git status --short
```

## 주의사항

- `git add .`로 범위 밖 파일을 포함하지 마세요.
- 사용자의 기존 변경을 되돌리거나 삭제하지 마세요. 기존 커밋을 amend하거나 이력을 재작성하지 마세요.
- hook이 파일을 수정하거나 커밋이 실패하면 현재 diff를 다시 확인하세요. hook을 우회하지 마세요.
- 커밋만 요청받았으면 push나 PR 생성까지 진행하지 마세요.
- 최종 응답에 커밋 해시·메시지와 남은 변경을 보고하세요.
